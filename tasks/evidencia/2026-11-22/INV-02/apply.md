# INV-02.apply — políticas en el escritor y compensaciones históricas

Base: `d05eae09d67ed0b190b6785da168a8fb8b564fd0` + árbol compartido. Código implementado y V1 local comprobada; sin aceptación dependiente ni V2 PostgreSQL independiente. No se aplicaron migraciones externas ni se habilitó venta de elaborado.

El escritor canónico selecciona el lector publicado cuando el servidor configura `SALES_RECIPE_POLICY_MODE=PUBLISHED`. Es una activación de despliegue posterior a preparar 0159/0160 y publicar las versiones; no es un parámetro HTTP. Un valor configurado distinto se rechaza al construir una nueva definición. La ausencia conserva temporalmente el despliegue previo mientras se preparan migraciones: no constituye la regla final de adopción de históricos ni cierra INV-02. Si ya existe una política para una receta visitada, esa transición bloquea ventas nuevas en vez de ignorarla; retirar la bandera no restaura el consumo mutable de una receta publicada. Un head publicado conserva el lector publicado aun al solicitar explícitamente otra versión.

Las correcciones de cantidad/ingreso y anulaciones conservan el snapshot y las asignaciones del head. Una versión posterior no reinterpreta las cantidades anteriores. Para una nueva identidad, remapeo o cambio explícito de versión se exige cobertura publicada al activar el modo; no hay fallback por ausencia de política, auditoría, versión o subreceta. Los errores SQL conservan sus códigos para el reintento transaccional completo; los errores de definición entregan PENDING_RECOVERY. Los snapshots elaborados se pueden calcular, pero el escritor rechaza cantidad positiva mientras falte PROD-01, incluso si hay stock físico del SKU. Se conserva la posibilidad de compensar a cero un hecho anterior.

El lector publicado y el recorrido legacy de transición comparten el advisory lock empresa/receta del publicador, por cada receta visitada. La lectura y la aplicación usan la misma transacción SERIALIZABLE/savepoint del escritor. Las pruebas locales no acreditan por sí solas carreras entre conexiones.

Se corrigió una brecha de retroactividad: las ventas del padre también protegen la subreceta. El publicador consulta los ancestros del grafo editable para proyecciones legacy y busca la receta en los snapshots canónicos congelados, incluso cuando la ficha actual dejó de referenciarla. La recursión usa UNION para no ciclar con referencias repetidas. Las relaciones históricas legacy que nunca tuvieron snapshot y ya desaparecieron del grafo actual requieren caracterización/recovery; no se atribuye conocimiento de una ficha histórica inexistente.
